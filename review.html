01

Problem

Code review is a queue: pull requests wait for a busy senior engineer, and the first pass is often mechanical. An automated first reviewer could shorten that wait, but only if engineers trust it. The fastest way to lose that trust is a confident comment about code that isn't in the change, or a "request changes" verdict built on a misread README.

So the hard part is not getting a model to write a review. It's making sure nothing the model invents reaches the pull request, and that a human can stop any review before it posts.

02

Architecture

  • Webhook routeVerifies the HMAC signature before parsing; with no secret configured it rejects everything.
  • Background taskReturns to GitHub at once and runs the review afterwards, since a review can take far longer than GitHub waits.
  • fetch_diffPulls PR metadata and the unified diff; anything past 80,000 characters is cut with a visible marker.
  • llm_reviewClaude, OpenAI or NVIDIA behind one interface; Claude caches the long system prompt. One 180-second bound per call.
  • parse_responseExtracts the JSON object; anything else raises, so a malformed answer never becomes a comment.
  • build_reviewKeeps only findings that quote a changed line, then sets verdict, summary and score floors in code.
  • persist_reviewSaves every review to MongoDB before the posting decision, so a held review is never lost.
  • Approval branchPosts when auto-posting is allowed; otherwise ends and waits for /review/approve.

    03

    Key decisions and trade-offs

    Ground every finding in the diff, and take the verdict away from the model

    ChoseEach finding must name a file in the PR and quote one of its added or deleted lines (at least 8 characters). Survivors decide the verdict: none means approve, any high or critical means request changes.
    RejectedRelying on prompt instructions alone and trusting the model's own verdict and summary. The prompt still asks for evidence, but nothing depends on the model obeying it.
    Trade-offReal issues whose evidence spans several lines, or sits in unchanged context, are dropped. The system prefers a missed comment to an invented one.

    Documentation can't testify about application code

    ChoseFindings on READMEs and repo metadata are allowed only as low or medium code-quality notes about that file, matched against a list of documentation terms.
    RejectedTreating all changed files equally. A README that describes a security risk would otherwise produce a "critical security" finding against code nobody changed.
    Trade-offA genuinely dangerous config change in a metadata file is capped at medium and can't block the merge on its own.

    Approval as a branch in the graph, after the review is saved

    ChoseA conditional edge after persist_review routes to posting or to a held end state, so the gate is visible in the pipeline's shape and tested as a path.
    RejectedA flag checked inside one long function, which is how the service worked before the graph was wired in, and posting first with a delete on rejection.
    Trade-offThe gate defaults to off so demos post straight away. A team using it for real should switch it on.

    Acknowledge fast, review in the background, fail once

    ChoseReturn to GitHub immediately and run the graph as a background task, with one 180-second bound per LLM call and SDK retries turned off.
    RejectedReviewing inside the webhook request, which outlasts GitHub's delivery timeout, and SDK retries that could stack several long waits on one review.
    Trade-offBackground tasks live in the server process: a restart loses an in-flight review, and transient errors aren't retried. A durable queue is the fix.

    Evaluation and results

    Review quality is not yet measured. There is no labelled set of pull requests yet, so there is no precision, recall or false-positive rate to report. What is tested is the behaviour around the model: what it is allowed to claim, and what happens to a review afterwards.

    Behaviour under testTestsResult
    Findings about files outside the PR are dropped1pass
    High-severity findings block only when evidence matches a changed line1pass
    READMEs can't be evidence for app-code claims; doc notes don't block2pass

      The LangGraph module couldn't even load (it imported a helper that no longer existed), so every review ran through a plain sequential method.
      Change
      Reviews now execute the compiled graph. The approval gate is a branch after the review is saved, and grounding and timeouts carry over. Signed webhooks and token auth became required, with tests in CI.

    6. Nov 2026One review per commitRedelivered and repeated webhooks no longer start a second review.+
      Problem
      GitHub redelivers webhooks, and opened or reopened events can arrive for a commit that was already reviewed. Each one started a full review and could post a second comment.

    06

    Failure modes and guardrails

    What goes wrongWhat the system does
    Model invents an issue in unchanged code or another fileNo changed line matches its evidence, so the finding is dropped and logged.
    Model claims "approve" or "request changes" on its ownIgnored. The verdict is recomputed from the findings that survived grounding.
    Model returns prose instead of JSONParsing raises; the background task logs the failure and nothing is posted.
    Provider hangsThe call is cut at 180 seconds with no retries; the review fails without posting.
    Forged or unsigned webhook401 before the payload is parsed. With no secret configured, every webhook is rejected.
    Very large diffCut at 80,000 characters with a marker; findings can only cite lines that were actually sent.
    Posting to GitHub failsThe review is already saved in MongoDB, so it can be approved and posted again.
    GitHub delivers the same event twiceThe first delivery claims the repository, PR and head commit; later ones are acknowledged as duplicates. A failed review releases its claim so a redelivery can retry.
    Server restarts mid-reviewNot handled. In-flight background work is lost. Known gap.
    07

    Limitations and what I'd do next

    • Build a labelled set of pull requests with seeded bugs and measure precision, recall and the share of model findings that grounding drops.
    • Move reviews from in-process background tasks to a durable queue with retries, the way I run task orchestration in production.
    • Ground multi-line evidence, so real issues that span several changed lines aren't dropped.
    • Add rate limiting on the API routes, and deploy a demo against a sandbox repository.
