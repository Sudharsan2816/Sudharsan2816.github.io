AI Workflow Automation

An LLM workflow in production at Edvoy. It reads the email thread behind each Jira ticket, works out what the case needs, and decides whether to act or bring in a person. The hard part wasn’t calling the model: it was deciding when the system may act on its own.

01

Problem

$ cat PROBLEM.md

At Edvoy, an existing automation already turned relevant incoming emails into Jira tickets. A ticket on its own is thin: the context that decides what should happen sits in the email thread behind it. And cases vary, so the same kind of ticket can need different decisions.

The system had to decide those cases without asking a person every time, and still bring a person in when a case needed one. That boundary is the hard part of the system, more than the model calls.

02

Architecture

pick a node

a case, end to end · 6 nodes

around it

Jira poller
Picks up new tickets and starts the pipeline. The tickets come from an existing mail-to-Jira automation that I didn’t build.
Thread retrieval
RAG over the email thread behind the ticket, so a decision rests on the whole conversation, not just the latest message.
Agent step
Runs on Hermes, an agentic AI platform. The model works out what the case needs and suggests what should happen; it doesn’t get the final say.
Decision directory
Records which decision applies to each kind of case, so varied cases get the right outcome without pulling a person in every time. Written from the business rules and from how users responded to the prototype.
Guardrails
Together with the decision directory, they decide the outcome: the system acts, or the case goes to a person.
Slack alert
Alerts the person responsible, so people are pulled in only when a case needs them.
n8n workflow
Orchestrates the steps above. The workflow and its pipeline are mine.
LangGraph extraction
LangGraph workflows in the same system extract requirements from university emails, documents and web pages.
Mail → Jira
The automation that creates tickets from incoming mail. It was already in place, and isn’t mine.

04

Decisions and trade-offs

$ git log --grep=decision
01

A decision directory, instead of asking a person every time
ChoseA directory that records which decision applies to each kind of case, written from the business rules and from how users responded to a working prototype.
WhyCases vary. A system that asks a person about each one only moves the work around; one that never asks will get some cases wrong.
CostThe directory covers the kinds of case written into it, so it has to grow as new kinds appear and as the rules change.
02

Retrieve the whole email thread, not just the ticket
ChoseRAG over the email thread behind each ticket before anything is decided.
WhyThe ticket is created from a single email; the context that decides the case can sit earlier in the thread.
CostEvery case pays for a retrieval step before a decision.
03

Guardrails last, built from a working prototype
ChoseRetrieval, then the Jira trigger, then Slack alerts, then the guardrails and decision directory.
WhyThe guardrails were written from how users responded to the prototype, so the prototype had to exist first.
CostThe system went live only once that last step was in.

06

Failure modes and guardrails

if → then

if a case clears the decision directory and guardrails

The system acts on it without pulling a person in.

if it doesn’t

Slack alerts the responsible person instead of the system guessing.

if the ticket alone lacks the context

Retrieval pulls it from the email thread behind the ticket.

if someone needs to know why it did something

Every agent call is logged.
