01

Problem

$ cat PROBLEM.md

External data arrived in many shapes, and every new kind needed cleaning before the rest of the system could use it. Separately, some university portals emailed a one-time code at login, which blocked end-to-end automation.

Both needed the same discipline: take messy, unpredictable input and turn it into something the next system can trust, without losing or repeating anything.

04

Decisions and trade-offs

$ git log --grep=decision
01

A pipeline for each new kind of data
ChoseModular pipelines: each new kind of data gets its own cleaning and conversion logic into the shared internal format.
WhyA new source doesn’t touch the pipelines that already work.
CostMore pipelines to look after: 25+ of them.
02

Codes as events, handled defensively
ChoseA watcher on webhooks and GCP Pub/Sub.
WhyThe code arrives as an event, so the automation can carry on without someone fetching it.
CostEvents can arrive twice or not at all, so every one is acknowledged, de-duplicated and timed out.

06

Failure modes and guardrails

if → then

if the same OTP event arrives twice

Duplicate detection drops the second one.

if no code arrives

A timeout ends the wait instead of leaving the run hanging.

if processing fails before an event is acknowledged

It isn’t acknowledged, so Pub/Sub delivers it again.

if a new kind of data appears

It gets its own cleaning logic; the existing pipelines aren’t touched.

if a step fails

Retries and failure recovery, with failures logged centrally in MongoDB.
