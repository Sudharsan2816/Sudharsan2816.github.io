Market Research Copilot

01

Problem

Market-research reports are dense: one page can carry a company's founding year, its price points, its growth rate and a competitor comparison. An analyst who asks a general chatbot about them gets fluent answers drawn from the model's memory, and the numbers are often wrong or invented. The useful version answers only from the reports the analyst uploaded, shows which passages it used, and says plainly when the reports don't cover a question.

So the job of this system is retrieval quality and refusal discipline, more than generation. If the right passage isn't retrieved, the best model in the world still answers badly.

02

Architecture

  • ParserReads PDF, CSV, TXT and Markdown; CSVs become 50-row text chunks so tables stay retrievable.
  • ChunkerFixed 305-word windows with 38 words of overlap, so facts at a boundary appear in both neighbours.
  • EmbeddingsNVIDIA NIM nv-embedqa-e5-v5, L2-normalised so inner product equals cosine. Falls back to local MiniLM if the API fails.
  • FAISSOne flat inner-product index per session, so one user's documents never answer another user's question.
  • Follow-upsPronouns and close typos are resolved against report entities; an optional Gemini call condenses the turn. Only the standalone query is embedded, never raw history.
  • Relevance floorDrops candidates under 0.35 cosine before reranking; if none survive, the answer is "not covered" with zero sources.
  • RerankerNIM nv-rerankqa-mistral-4b-v3 orders 20 candidates and keeps 6; if the endpoint is down, embedding order is kept.
  • GeneratorNVIDIA Nemotron, prompted to answer only the current question from the supplied chunks, with citations.
  • Report workersLong market reports run in server-owned jobs with progress stages and restart recovery, capped at 10 active jobs.
  • APIFastAPI with optional API-key auth, rate limiting, sanitised uploads and request IDs on every log line.
03

Key decisions and trade-offs

Fixed-size chunks over semantic chunking

ChoseFixed windows. On 32 labelled questions, complete-hit@3 was 100% against 90.6% for semantic chunking, and evidence recall@3 100% against 93.75%.
RejectedSemantic chunking. It split related facts that sat on one dense page, and doubled the chunk count, so narrow chunks competed for the same top-3 slots.
Trade-offSemantic chunks cut retrieved context by 44.5%, which would lower prompt cost. Missing evidence costs more than extra tokens for a research tool.

305 words, picked by a sweep, not a round number

Chose305/38. It kept hit@3 and hit@6 at 100% and gave the best top-1 result: 71.9% hit@1 and 0.885 MRR, against 62.5% and 0.839 at 800/100.
Rejected285/36, the smallest size with perfect hit@3, because its hit@1 and MRR were lower. Below 280 words, some evidence fell out of the top three.
Trade-offAbout 87 more context words at top 3 than 285/36, accepted for better first-result accuracy.

Filter, then rerank, except for comparisons

ChoseFAISS fetches 20, a 0.35 floor removes weak matches, then NIM reranks to 6. Comparative questions skip the floor and diversify sources first.
RejectedFlooring every query. A "Nimbus vs Corvex" question needs evidence from both reports, and the floor can discard one side before the reranker sees it.
Trade-offComparisons can pass weaker candidates to the generator. The reranker's lift over embedding order has not been measured separately yet.

Embed the question, never the conversation

ChoseResolve "its" and near-miss names against entities in the reports, then embed one standalone question.
RejectedEmbedding raw history. In the live test, earlier turns leaked into answers: a Tesla question came back repeating the previous France question.
Trade-offEntity matching is deliberately strict, so a misspelling far from any report entity stays unresolved instead of guessing.

Regression suite

A committed six-case evaluation scores recall@3, hit@3, citation precision and recall, and a claim-token faithfulness check; all are 1.00 and gate CI. The faithfulness check is deterministic, not a model judge, and six fixture cases measure regressions, not general answer quality. 96 automated tests run in CI.

Failure modes and guardrails

What goes wrongWhat the system does
Question isn't covered by the reportsNothing clears the 0.35 floor, so it returns "Not covered in the uploaded documents." with zero sources. The LLM is not called without context.
A related but different fact exists (gross vs net margin)Says the asked metric is not covered instead of substituting the nearby one.
Reranker endpoint unavailableKeeps FAISS embedding order and continues.
Embedding API failsFalls back to the local MiniLM model.
Earlier turns contaminate the answerOnly the standalone current question is embedded, and the prompt answers only the final question block.
Unknown or badly misspelled entityStrict matching leaves it unresolved, so it is refused rather than mapped to the wrong company.
One user's documents answering another's questionSeparate FAISS index per session; session IDs are validated against path traversal.
Browser tab closed during a long reportReport jobs belong to the server, persist progress and recover after restarts.
06

Limitations and what I'd do next

  • The chunking benchmark used a 6-page corpus. Re-run it on a larger labelled set before treating 305/38 as general.
  • Measure the reranker's lift on its own, with the same questions run with and without it.
  • Add an independent model judge and adversarial questions (prompt injection inside documents, near-duplicate entities) to the evaluation.
  • Allocate retrieval by a context-word budget as well as by chunk count, so smaller chunks don't lose slots.
  • Host a public demo; the NVIDIA free tier's latency spikes need a timeout and a visible retry first.
