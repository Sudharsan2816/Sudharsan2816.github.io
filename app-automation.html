Application Automation

A pipeline that fills in and submits applications on university portals, where every portal has its own steps and rules. Released as a prototype in March 2026 and in production since May, it has made 3,400+ submissions, and about 95% of its runs succeed.

As Junior Data Engineer: designed the initial architecture, built the pipeline and its logic, wrote the university configurations, split it into three containers. After my promotion: optimised it in production.

01

Problem

$ cat PROBLEM.md

Every application to a university goes through that university’s own portal, and every portal behaves differently: different steps, different fields, different rules. By hand, one submission took about 30 minutes.

The system had to run many submissions at once, keep one failure from stopping the rest, and take on a new university without new code.

02

Architecture

pick a node

one submission · 5 nodes

around it

Task queue
RabbitMQ. Each submission becomes a task, scheduled asynchronously and run in parallel, and a failed one can be retried without holding up the rest.
Pipeline logic
The steps every submission follows, shared across universities. I built the pipeline and the logic it follows.
University config
What differs per university lives in its configuration, not in new code. I wrote the university-specific configurations; 70+ portals run this way.
Browser bot
Fills in and submits the application on the portal, staying in contact with the pipeline through the browser’s native host.
Run result
Each run ends as successful or failed. That’s what the ~95% counts; runs a user stopped are left out.
Three containers
I dockerised the project and split it into three containers, so one failing feature can’t take the whole system down.
AWS
Runs on AWS. Moving off local machines fixed the native-host disconnects that stalled the bot. The move was my manager’s idea; I did the work, after my promotion.
New data types
After my promotion, I extended the pipeline to take new kinds of data without code changes.

04

Decisions and trade-offs

$ git log --grep=decision
01

A queue between the work and the bot
ChoseRabbitMQ tasks: each submission is queued, scheduled asynchronously and run in parallel.
WhySubmissions run side by side instead of one after another, and a failure is retried on its own instead of stopping the batch.
CostA broker to run and watch, and every task has to be safe to retry.
02

Three containers instead of one
ChoseThe project dockerised and split into three containers.
WhySo one failing feature can’t take the whole system down.
CostThree things to deploy and keep in step instead of one.
03

Each university as a configuration
Chose70+ university configurations on one shared pipeline. The approach was the platform lead’s; the configurations are mine.
WhyA new portal is new configuration, not new code.
CostThe configuration has to capture everything that differs between portals, and when a portal changes, its configuration has to change with it.

06

Failure modes and guardrails

if → then

if one submission fails

Its task is retried from the queue; the other submissions keep running.

if one feature fails

It’s in its own container, so the other two keep running.

if the browser’s native host disconnects

Running locally, the bot lost contact with the pipeline and stalled. Moving the project to AWS fixed it.

if a portal emails a one-time code at login

The platform hands the code to a person. An earlier version caught these automatically (see Pipelines and events).

if a new university is added

It’s a new configuration on the same pipeline, not new code.

if a user stops a run

It isn’t counted as a success or a failure in the ~95%.

What this page doesn’t show

  • ~95% is a run success rate, measured as successful ÷ (successful + failed), with runs a user stopped left out. It isn’t an accuracy figure.
  • ~5 minutes is the bot’s own time per submission. It leaves out pauses where a person steps in, such as entering a one-time code.
  • 3,400+ is the total since the first release in March 2026, not a daily figure.
  • It’s an internal Edvoy system: no code, data, university names or screenshots are public.
